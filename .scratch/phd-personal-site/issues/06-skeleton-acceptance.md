## Question

本图的终点是「设计文档 + 能跑的最小骨架」。要把「怎么算跑通」定成可以逐条打勾的标准，否则骨架会一直处于「好像差不多了」的状态。

1. **骨架必须包含什么**：4 个页面（首页/论文/项目/分享）+ 详情页模板？还是先不管分享详情（因为分享是空的）？
2. **样例数据**：2 篇真实论文 + 1 个真实项目。这 3 条由 owner 提供真实内容，还是先用占位假数据把结构跑通？（真实内容能验证字段够不够用，但需要 owner 花时间整理）
3. **跑通的判定**：`npm run dev` 能开、四个页面能访问、论文详情能打开、图片能显示、`npm run build` 无报错 —— 还需要什么？
4. **设计文档写到什么颗粒度**：只写结论，还是连每个字段的填写示例都要给？
5. **设计文档放哪**：`.scratch/phd-personal-site/` 下，还是 `docs/` 下（与已有两份调研文档并列）？
6. **样式要做到什么程度**：完全裸 HTML、还是一套最简 CSS（能读、移动端不溢出、不追求美观）？

>
> 1. **`getStaticPaths()` 返回 `[]` 时，组件函数体（frontmatter + 模板）执行 0 次**，只有 `getStaticPaths()` 与它 import 的模块会跑。硬证方式：在模板里放 `throw new Error(...)`，0 条时命中 0 次、构建 exit 0；同一份模板塞 1 条后立刻 `[ERROR] Caught error rendering` 并非零退出。⇒ **`astro build` 通过 ≠ 该模板被验证过。**
> 2. **空集合的两条警告消不掉**：目录不存在是 `The base directory ... does not exist.`，存在但为空是 `No files found matching "**/index.md"`；`.gitkeep` 只是把前者换成后者，而 `The collection "notes" does not exist or is empty.` 无论如何都在（源码 `hasCollection` 只认 `store.set()` 过的集合，0 文件从不 set）。⇒ **「警告为零」不能写进验收，它是永远打不上的勾。**
> 3. **本机失败构建的退出码有时是 `-1073740791`（`0xC0000409`），不是 `1`**。⇒ 验收脚本只能断言 `exit != 0`。另：Astro 7 已用 `render(entry)` 取代 `entry.render()`，旧写法直接构建失败，而往返验证一定会用到它。
>
> 附带核实：集合目录不存在 vs 空目录，**构建结果、exit code、`getCollection()` 返回值（都是 `[]`）三者完全相同**，只差警告文案；`[...slug].astro`（rest）返回 `[]` 与 `[slug].astro` 行为**完全一致**，社区「rest 空数组会产出 404」的说法不成立；Astro **没有** Next.js 式「至少一个页面」限制（极端构造下 `0 page(s) built` 仍 exit 0）；`dist/notes/index.html` 与 `dist/notes/` 共存正常，0 条时动态路由不产生竞争。**仍未覆盖**：`build.format` 非默认值、`getEntry()`、增量构建，已列在笔记末节。

## Answer

> 裁定日期 2026-11-17。第一性原理：**「构建通过」不是验收标准，因为它在最该报警的地方最安静。**
>
> 这条不是修辞，是本票查出来的硬事实：分享详情页的模板在骨架期**一次都不会被执行**（组件函数体执行 0 次），所以它在构建日志里无论写得多错都是全绿的。凡是「写错了也不报错、只是页面悄悄坏掉」的地方，验收就必须换成能让它出声的手段——这与 #4 / #5 / #6 那条「宁可构建失败，也不让页面悄悄错」是同一条判据在本票的延续。

### 1. 样例数据：全真实，因为假数据证明不了目的地

目的地的措辞是「骨架里真的填进了 2 篇论文和 1 个项目，**能证明字段够用**」。占位假数据的证明力只到「模板不报错」为止——它能通过 `figures[0]` 取图，能通过 `.min(1)` 校验，但它不能告诉你「真实论文的作者有 9 个人、`me: true` 落在第 3 位时模板排版会不会崩」。

成本已经被 #4 压到很低：它把两篇真实论文写成了可直接抄的形态（Attention Is All You Need 2017 / Deep Residual Learning 2016，标题、年份、会议、DOI、全部作者均按真实信息填），唯一要替换的是 `me: true` 那一行与名次。

- **论文配图**：从论文 PDF 截原图，`caption` 用原图注的中文翻译。这比自画示意图省事，且语义正确（图注本就是给图做说明的）。**不放开 `.min(1)`**——那要推翻 #4 的裁定，而 #4 的理由（`<Image />` 的 `alt` 缺失即构建报错）仍然成立。
- **项目条目**：用真做过的东西即可，不必开源——`repo` / `demo` 在 #5 里都是可选字段，`shots` 的 `.min(1)` 一张截图就够。

### 2. 图片压缩：在本票内裁掉，不另开工单

只有 4–5 张图（1 个项目截图 + 2 篇论文各 1–2 张），标准定一次够用半年，独立开票的仪式成本大于收益。定：

| 项 | 值 |
| --- | --- |
| 长边 | ≤ 1600 px |
| 格式 | `.webp`（Astro 构建期也会转 webp，#4 已确认 `src/` 图构建期转码） |
| **单张体积** | **≤ 300 KB**（#5 确认该设限的是体积不是张数，这条终于把它落到实处） |
| 工具 | `npx sharp-cli`（一次性，无常驻依赖）或在线 squoosh |

地图的 Not yet specified 里那条随本票删除。

### 3–4. 设计稿：写到「三个月后的你不用再读票」

**位置**：`docs/design/站点设计稿.md`。仓库里已有约定可查——README 第 15 行写 `.scratch/` 是「规划工作区（**不参与构建**）」，第 37 行写 `docs/research/` 是成品文档；地图「已定事项」也写「`docs/` 与源码平级」。

**不选 `.scratch/` 的理由是生命周期**：`.scratch/` 存的是过程材料（票、地图、调研草稿），它的寿命随 effort 结束而结束；设计稿是成品，要活到下一个 effort。放错地方，下一个 session 会把它当「上一轮的草稿」而不是「这一轮的规范」。**单文件不拆**——拆开就找不到。

**颗粒度**：结论 + 每字段填写示例 + 新增内容操作步骤 + 移交清单。判据是这份文档的读者——三个月后的你，和下一个 session 的 agent。只写结论的话，想加一篇论文就得回去翻 #4 的 11244 字正文加 4 条补遗评论，而那里 schema 还是 camelCase（以补遗为准）——这种「正文与补遗分离」对人极不友好。

**注意**：#4 / #5 / #6 已经把 schema、2 篇样例、排序函数、降级规则全产出了，设计稿只是**收拢组装**，不新写。

### 5. 样式：最简 CSS，但「最简」必须是可测量的

完全不写 CSS 的问题不是难看，是**让验收无法执行**：浏览器默认样式下「移动端不溢出」根本无法测量（中文长句不换行就横向滚动），而这正是 `docs/research/个人网站执行清单.md` 阶段 4 明确要求的三档宽度检查。完整设计系统则撞上地图 Out of scope 的「完整视觉 UI 设计」。

三条硬约束：

1. 全局 `src/styles/global.css`，只用 4 个 CSS 变量（文字色 / 背景色 / 最大宽度 / 行高）
2. 320 / 768 / 1440 三档无横向滚动 —— 靠 `img { max-width: 100%; height: auto }` + 正文 `max-width`
3. 不引任何 CSS 框架、不引任何外部字体

### 6 & 10. 8 条路由全落地，分享详情页用往返验证

| 路由 | 产物 |
| --- | --- |
| `/` | `dist/index.html` |
| `/papers/`、`/papers/<slug>/` | `dist/papers/index.html`、`dist/papers/<slug>/index.html` |
| `/projects/`、`/projects/<slug>/` | 同上结构 |
| `/notes/`、`/notes/<slug>/` | 同上结构 |
| `/404.html` | `dist/404.html` |

原问第 1 题给的是「要不要先不管分享详情（因为分享是空的）」。实测给出第三条路：**必须写，但它的验证方式完全不同**。

`notes/[slug].astro` 在 0 条内容时组件函数体执行 **0 次**，构建通过对它零信息。但它如果写错了，错误会**推迟到第一篇文章进来的那一刻**才爆发——而那时你可能已经忘了它的存在，且那时你会在「加内容」的心智状态下遇到一个「模板写错了」的报错，归因成本极高。

所以：**往返验证**。临时塞 1 条 notes 内容 → 断言 `dist/notes/<slug>/index.html` 里出现那条内容的真实 `title` 文本 → 删除 → 再次构建 exit 0 且 `dist/notes/` 只剩 `index.html`。这是唯一能证明该模板没写错的手段；顺带也验证了 `render(entry)` 这个 Astro 7 新 API 在本项目里能用（旧写法 `entry.render()` 已失效，笔记里有实测）。

### 7 & 8 & 11. 验收的三种形态

**自动（`npm run verify`，8 条断言）**：

| # | 断言 |
| --- | --- |
| 1 | `astro build` 退出码 **`!= 0` 即失败**（不断言 `== 1`，实测有 `-1073740791`） |
| 2 | 输出无 `[ERROR]` |
| 3 | **警告白名单**：允许 notes 的两条，**禁止**出现 `base directory ... does not exist`（这条能判断 `.gitkeep` 在不在） |
| 4 | 8 条路由对应 `index.html` 逐个存在 |
| 5 | `dist/notes/` 下**无子目录**（0 条时不该生成详情页） |
| 6 | 往返验证（第 10 节） |
| 7 | 内部断链：扫全部 `dist/**/*.html` 的 `href` / `src`，逐个断言目标存在 |
| 8 | 图片：`<img>` 数量 ≥ 4，且对应源文件存在于 `src/content/**` |

第 3 条是**白名单而不是清零**，这是本票对原问第 3 题最重要的一处修正：「无警告」是永远打不上的勾，写成验收项就是自欺。第 7 条是唯一能自动发现「链接写错」的手段，值得写。第 8 条专治「图裂了」——它只能查 HTML 里有没有 `<img>` 与源文件在不在，查不出渲染结果，所以仍需人眼补一刀。

**人工（2 条，进程长驻，不进脚本）**：`npm run dev` 打开一次确认四个页面可访问；`npm run preview` 验一次构建产物。

**人眼（5 条，压到最短）**：

1. 320 / 768 / 1440 三档无横向滚动
2. 图真的显示出来（不是破损图标）
3. 只看键盘 Tab 能走完全站
4. 中英文标题主次符合 #6（`title_zh` 主、`title_en` 小字）
5. 空态文案是 `暂无分享。`

**落地形态**：`.gitkeep` 与警告白名单都做成仓库里的**实体文件**，不写成设计稿里的一句约定——约定会漂移，文件不会。将来有人在 `notes` 里加内容，警告自然消失，白名单那条不再匹配，脚本不会因此误报。

`.gitkeep` **必须有**，但理由要写对：实测空目录不被 git 跟踪，`git clone` 后消失；加了就保留。它的作用是**让新 clone / CI 不退化成更差的「目录不存在」警告态**，**不是**消警告——笔记里确认 0 文件时 `The collection "notes" does not exist or is empty.` 无论如何都在。

`scripts/verify.mjs` 用 Node 原生能力手写，不引测试框架：省一个常驻依赖，且这 8 条断言都不需要框架。

### 12. 设计稿与移交：只存在于已关闭票里的信息等于丢了

设计稿必须自带「已知风险与移交」一节，收拢 5 条：

| 事项 | 来源 | 为什么必须移交 |
| --- | --- | --- |
| EdgeOne 对无尾斜杠访问的实际响应 | #3 | 需先部署才能测 |

| `index` 去尾、`prerenderConflictBehavior` 作用于条目 slug | #4 | 均为源码行为、文档未写，跨大版本升级时复核 |

### 13–14. 两个施工前置

**包管理器：npm**。本机 npm 12.2.0 已就绪；`.gitignore` 里同时留着 `.pnpm-store/` 与 `pnpm-debug.log`，说明当初没定。这不该悬空——lock 文件选错，后面每次装依赖都是两种工具混用。提交 `package-lock.json`；`.gitignore` 那两行 pnpm 条目保留无害，不用动。

**开工前先清工作区**：`git status` 当时是脏的——`M` 4 个 `.scratch/` 文件（map.md 与 #3/#5/#6 的仓库副本），`??` 4 份调研笔记从未提交。地图有一条纪律「建骨架前先 `git init` 并完成首次提交」——`git init` 早已完成（3 次提交），但纪律的精神是「骨架开工前仓库得干净」。不处理的话，骨架的第一个 commit 会混进规划期改动，`git log` 里分不清哪次是骨架起点；而且那 4 份笔记目前只存在于本地，机器出事就没了。⇒ 单独提交一次，message 写「规划阶段收尾：地图与调研笔记入库」。
